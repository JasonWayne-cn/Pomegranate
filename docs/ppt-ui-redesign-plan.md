# PPT 生成页界面重构方案

> 状态：已实现（2026-11-28）
> 范围：前端 `src/pages/ppt/index.tsx`、`src/lib/api/extension.ts`、`src/types/extension.ts`；
> Rust `commands/ppt_extension.rs`、`services/ppt_extension.rs`；引擎 `extensions/ppt-master/entry.py`（版本 1.2.7）
> 基线：本文行号基于当前 `main` 分支代码，实现时以函数名/锚点为准

### 实现落点

- 右侧 `StepRail` 取代顶部 Steps；删除「打开 Office」按钮、副标题与横向导航条。
- 步骤 ② 使用 `renderDraftWorkspace({ showPreview: false })`，只保留文案编辑。
- 步骤 ③ 左模板列表 + 右「程序模板生成」预览（`previewPages/previewSvgs` 独立状态）。
- 静态提示改为卡片标题 `StepTitle` 的 ⓘ Tooltip；动态警告/结果 Alert 保留。
- 后端新增 `PptDraftKind`：`preview` → `svg_preview`，`formal` → `svg_output`；
  `render_draft/list_draft_pages/read_draft_page` 均带 `kind`，完成事件带 `kind`。
- 引擎按 `options.renderTarget` 选择输出目录；扩展包已重建为 1.2.7。

---

## 1. 背景与目标

当前 PPT 生成页纵向空间利用率低：顶部横向 5 步流程 + 两行说明 + 全宽蓝色提示框 + 每页操作条占据约一半首屏，真正的编辑/预览区被挤到下方。

目标：

1. 5 步流程改为**右侧竖向编号列**，常驻可见、可直接点击导航。
2. 蓝色静态提示框改为**页面标题旁的 ⓘ 悬停提示**（Tooltip）。
3. 通过右侧步骤列**直接导航**，删除每页的「返回上一步/返回素材/返回当前步骤」等按钮。
4. 「制定大纲」页不再显示页面预览，只做纯文本大纲编辑。
5. 「效果与模板」页改为**左侧模板列表 + 右侧程序模板生成预览**。

## 2. 信息架构（五步流程不变）

| 步骤 | 名称 | 职责 | 视觉产物 |
|---|---|---|---|
| ① | 设置与素材 | 选文档 / 本地文件 / 补充素材 / 生成要求 | 无 |
| ② | 制定大纲 | 生成、编辑、排序、增删大纲页 | 无（纯文本） |
| ③ | 效果与模板 | 选版式模板 / 图表 / 原生图表 + 程序化预览 | 程序化 SVG |
| ④ | 草稿预览 | 单候选 / 三候选 AI 生成，逐页确认 | AI 生成 SVG |
| ⑤ | 导出 | 导出 PPTX、打开文件/目录 | 无 |

> 关键变化：视觉预览从「步骤 ②」后移到「步骤 ③」，步骤 ③ 承担"选模板 + 看效果"。

## 5. 交互规范

### 5.1 右侧步骤导航：推进 vs 只读预览

现状：`viewStep`（当前查看）与 `step`（真实流程）分离；未来步骤只读预览。

新规则（替换 `handleStepChange` 中 `next === 3 && step === 2` 的特例）：

```ts
const canReach = (n: number) =>
  n <= 1 ? true
  : n <= 3 ? !!plan
  : formalized || job?.stage === "draft_ready";

function handleStepChange(next: number) {
  if (next === viewStep) return;
  if (busy) { message.info("正在生成中，暂不能切换步骤"); return; }
  if (next > step && canReach(next)) setStep(next); // 真正推进
  else setViewStep(next);                          // 只读回看/预览
}
```

- 点击**已到达**的步骤 = 只读回看，不改变真实 `step`，右栏标记「当前步骤」仍在原处。
- 点击**未到达但可到达**的步骤 = 推进真实流程。
- 点击**不可到达**的步骤 = 只读预览占位（`StepPreviewPlaceholder`），右栏显示「预览」标记，不显示全宽蓝色横幅。
- `useEffect(() => setViewStep(step), [step])` 保留，流程推进时视图跟随。

### 5.2 提示信息规范

| 类型 | 表现 | 示例 |
|---|---|---|
| 静态说明 | 标题旁 `ⓘ` + Tooltip | 「本步骤做什么」 |
| 动态警告 | 内联 Alert（warning） | 未选模板、文案已修改、程序化草稿 |
| 结果反馈 | 内联 Alert（success/error） | 导出完成/失败 |
| 进度 | 内联 Progress/日志 | 大纲规划、渲染、导出 |

- 卡片标题：`标题 + 灰色一行短说明 + ⓘ（长说明 Tooltip）`，短说明保证可发现性。
- ⓘ 图标常显、可键盘聚焦（AntD Tooltip），不依赖用户猜。
- 仅转换 4 处静态说明：大纲、模板、草稿预览、步骤占位提示。

### 5.3 删除的按钮清单

| 位置 | 按钮 |
|---|---|
| 顶部预览 Alert | 返回当前步骤 |
| 大纲页 | 返回素材、下一步：选择效果与模板 |

## 7. 风险与对策

1. **步骤 ③ 程序化预览污染步骤 ④ 状态**
   两者共用 `draftSvgs`/`job`。进入步骤 ④ 会看到程序化结果，与「进入本步不自动生成」冲突。
   对策：步骤 ③ 预览写入独立状态 `templatePreviewSvgs`；或步骤 ④ 顶部显示「当前为程序化预览，可点击生成 AI 草稿」。

2. **删除大纲预览后，`pageSelection`/候选页数据源失效**
   outline 分支不得请求候选数据，否则每次选页都会打接口。

3. **步骤 ④ 生成方式与步骤 ③ 重复**
   建议步骤 ④ 仅保留单候选/三候选；若保留程序模板生成，需在文案上区分「快速定版」与「AI 精修」。

4. **窄窗口空间**
   `minWidth=1000`。右栏 + 模板列表双重占宽，1280 以下：右栏图标化、模板列 200px、缩略图缩小。

5. **只读回看时的编辑权限**
   回看已完成步骤仍允许编辑文案（现状如此），需在右栏明确「当前步骤」标记，避免误以为流程倒退。

## 10. 补充方案 A：预览与草稿都采用模板（含分目录隔离）

> 本节补充/覆盖 §4.3 的“程序化预览”实现，并解决 §7 风险 1。
> §4.2「制定大纲」仍保持纯文本、无预览；视觉预览从步骤 ③ 开始。

### 10.1 目标

- 步骤 ③ 的预览**真正套用所选模板**（版式 + 配色 + 占位符结构），不再只是程序化 motif + 调色板。
- 步骤 ④ 的草稿同样基于同一模板：
  - 「程序模板生成」= 引擎结构化模板填充（确定性，与预览同一套模板映射）；
  - 「单候选页 / 三候选页」= AI 以模板的 `spec_lock` / template reference 为引导生成（仍是模板风格，但不是占位符确定性套用）。
- 预览与草稿产物**互不覆盖**，可来回切换步骤查看。

### 10.2 引擎能力（已具备）

扩展 `ppt-master` 的 `entry.py` 已实现：
- `fill_structured_layout`：处理 `data-pptx-placeholder` 结构化版式；
- `fill_layout_svg`：处理 `{{TITLE}}` 等文本占位符；
- `choose_page_type / alternate_page_type`：按页序与内容把大纲映射到 cover/contents/chapter/content 等模板页；
- 图表占位符与 `chart` 片段也可填充。

现有 `ppt_extension_render_draft(jobId, layoutId, chartIds, nativeCharts)` 即走这条确定性填充路径（引擎 `render` 阶段），前端目前未接入。

### 10.3 目录与 kind 隔离

```
project/
├── svg_preview/          # 步骤 ③ 模板预览（只读展示）
├── svg_output/           # 步骤 ④ 草稿（导出只读这里）
├── candidates/
│   ├── preview/          # 预览候选（模板填充无候选时为空）
│   └── formal/           # AI 候选（单/三候选页）
├── page_selection.json   # 仅正式：评分、签名、断点续跑
└── template_render.json  # 预览渲染签名（模板 + 图表 + 计划 hash）
```

- `DraftKind = "preview" | "formal"`。
- 新增/调整接口都带 `kind`：
  - `ppt_extension_render_draft(..., kind)`：引擎输出目录按 kind 选择；
  - `list_draft_pages(jobId, kind)` / `read_draft_page(jobId, file, kind)`；
  - `page_candidates(jobId, page, kind)`；
  - `ppt-extension://draft-page`、`plan-progress` 等事件带 `kind`。
- 导出、诊断、`count_draft_pages` 只读 `svg_output`。
- 正式草稿沿用现有复用签名与断点续跑；预览不使用 `page_selection.json`，无评分/候选。

**引擎输出目录的实现方式（二选一）**：
1. **扩展引擎支持 target（推荐）**：`job.json options.renderTarget = "preview" | "formal"`，`entry.py` 写入 `project/svg_preview` 或 `project/svg_output`。需要扩展包发版（manifest/version 同步）。
2. **Rust 侧兜底**：引擎仍写 `svg_output`，完成后由 Rust 将 `P*.svg` 移动到 `svg_preview`；仅适合“预览总是最后一次渲染”的场景，不能安全处理正式后再次预览，故不推荐。
3. 备选：把 `fill_structured_layout` 逻辑移植到 Rust，直接按 kind 写目录；可避免引擎依赖，但实现量较大。

### 10.4 前端调整

- 步骤 ③「效果与模板」：
  - 点选模板 → 标脏；
  - 点「生成模板预览」→ `updateJobOptions(layoutId, chartIds, nativeCharts)` + `renderDraft(kind="preview")`；
  - 右侧显示 `svg_preview`，页签切换；不再调用 `renderAiDraft(programmatic)`；
  - 切换模板后旧预览标记为过期，需重新生成。
- 步骤 ④「草稿预览」：
  - 生成方式保留「单候选页 / 三候选页」；「程序模板生成」若保留，也写 `kind="formal"` 的模板填充；
  - 进入本步骤不自动生成；只读 `svg_output`。
- `renderDraftWorkspace` 增加 `kind`：
  - `loadDraft(jobId, kind)`、事件按 kind 过滤；
  - 步骤 ③ 不显示候选/评分/复用信息；步骤 ④ 保留；
  - 引擎日志可按 kind 分开展示（预览日志与正式日志不混）。
- 切换步骤时按 kind 懒加载对应目录；不在内存里常驻两份状态（先采用“切步骤重新读取”，后续如需再改双缓存）。

### 10.5 清理与迁移

- 大纲变化 / 重新生成大纲：清空 `svg_preview` + `svg_output`（并清空正式选择）。
- 模板 / 图表 / 原生图表变化：清空 `svg_preview`；正式目录按现有签名规则决定是否清空。
- 旧作业：`svg_output` 视为正式草稿；`svg_preview` 不存在时步骤 ③ 显示空态，生成一次预览即可。
- 删除作业：连同两个目录一起清理。

### 10.6 验收补充

- [ ] 步骤 ③ 选择不同模板，预览的版式与配色随模板变化；未选模板时显示「中性」。
- [ ] 步骤 ③ 的预览写 `svg_preview`，步骤 ④ 草稿写 `svg_output`，互不覆盖。
- [ ] 正式生成后回到步骤 ③ 再预览，不会破坏已生成的正式草稿。
- [ ] 「程序模板生成」的正式草稿与同模板预览版式一致；AI 草稿受模板引导。
- [ ] 导出仅包含 `svg_output` 的页面。
- [ ] 旧作业可正常打开并重新生成预览。

### 10.7 风险

1. **扩展包需发版**：引擎写入目标目录依赖 `renderTarget` 参数；未升级前只能走 Rust 移动兜底。
2. **模板页型与大纲页数不固定**：模板 9–14 页，但大纲可任意页数；依赖 `choose_page_type/alternate_page_type` 复用页型，需验证长/短大纲的版式稳定性。
3. **图表占位符**：模板图表页与「原生图表」开关组合需要回归；无合适占位符时回退程序化图表。
4. **性能**：每次预览启动 Python 引擎有固定启动成本；后续可考虑常驻引擎或模板预编译缓存。
5. **状态复杂度**：kind 贯穿渲染、列表、读取、事件、清理链路，需统一常量与单测覆盖（路径、清理、事件过滤）。
